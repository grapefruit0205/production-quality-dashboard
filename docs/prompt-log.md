# 프롬프트 기록 — AI를 어떻게 썼는가

면접에서 "AI를 어떻게 활용했나요?" 에 대한 근거 자료입니다. 결과물만 남기지 않고 **어디를 사람이 판단했는지**를 함께 적었습니다.
이 프로젝트는 ①·② 에 이어 세 번째이며, **앞선 두 프로젝트에서 실제로 겪은 오류를 설계 조건으로 미리 넣고 시작**했습니다.

## 1. 사용한 요청(프롬프트) — 요지

| 순서 | 요청 | AI가 낸 것 | 사람이 판단한 것 |
|---|---|---|---|
| 1 | "①·② 와 같은 계열로 생산·품질 대시보드를 만들어 줘. 시트 탭 구성·KPI 6개·차트 6개·리포트 PDF·엑셀 내보내기·월간 트리거. ② 의 도구 함수(재시도·캐시·3단계 내보내기·자가 진단)를 그대로 재사용" | `Code.js` / `대시보드.js` / `설치.js` 3파일, 합본 `설치_한번에.js`, 로컬 하네스 | 회사·라인·인명은 전부 가상. 단위는 포(25kg). 비율은 전부 % 숫자로 통일 |

## 2. AI 답을 그대로 쓰지 않은 부분

- **월 키가 날짜로 바뀌는 문제**: AI 초안은 `2025-10` 을 그냥 썼습니다. 구글시트는 이런 문자열을 날짜로 바꿔 저장해 `SUMIFS` 가 0을 돌려줍니다(②의 점검일이 Date 로 바뀌었던 경험). → 텍스트 서식(`@`)을 먼저 주고 쓰고, 생산일보의 `월` 열은 `TEXT()` 수식으로, `설치_확인` 이 타입을 검사하도록 바꿨습니다.
- **조건부 서식의 다른 시트 참조**: "라인별 불량률이 목표를 넘으면 빨강" 을 AI 는 `목표!` 시트를 참조하는 수식으로 냈습니다. 구글시트·엑셀 모두 조건부 서식에서 다른 시트 참조가 안 됩니다. → 같은 시트에 목표 열/기준값 행을 두고 그것만 참조. 하네스에도 "다른 시트 참조면 거부" 스텁을 넣었습니다.
- **파레토 정렬**: 수식만으로 정렬(`SORT`·`LARGE`)하자는 안은 엑셀 비호환(`SORT`)이거나 동점 처리가 불안정해서, **갱신 시점에 스크립트가 순서를 정하고 수식(SUMIFS)은 그 순서로 쓰는** 절충안을 택했습니다.
- **리포트 값의 출처**: 대시보드 카드(수식)를 리포트가 그대로 읽으면 하네스에서는 수식 문자열밖에 못 얻고, 실제 환경에서는 수식 계산 타이밍에 따라 빈 값이 될 수 있습니다. → 리포트·코멘트는 스크립트가 생산일보를 **한 번 읽어 직접 합산**한 값을 쓰고, 정의(불량률·가동률·달성률)는 시트 수식과 같게 맞췄습니다.
- **개인정보**: 지원자 메일 주소·실제 회사명·실명을 코드·문서·저장소에 넣지 않았습니다. 메일 알림 주소는 `설정` 탭에 사용자가 직접 넣는 값(기본 비어 있음)입니다.

## 3. 하네스가 잡은 것 (구글에 올리기 전에 수정)

| 증상 | 원인 | 수정 |
|---|---|---|
| 회귀 테스트 "시간제한 0초" 가 멈추지 않음 | `Number(설정값) \|\| 270` 이 0 을 '비어 있음' 으로 보고 기본값을 씀 | 의도한 동작(빈 값 → 기본값)이라 코드는 유지, 테스트를 0.001초로 변경하고 문서에 명시 |
| 측정로그 정리가 빈 줄 1행만 지움 | 하네스에서 전부 빈 행을 `appendRow` 하면 `getLastRow` 가 세지 않음 — 실제 시트도 같음 | 테스트 데이터를 "측정일시만 빈 줄" 처럼 실제로 생길 수 있는 형태로 교체 |
| 회귀 테스트 후 `설치_확인` 이 측정로그 중복 3건을 경고 | 하네스는 0.1초 안에 끝나 실행 시각·소요초가 전부 같아짐 → 정리 함수가 (정확히) 중복으로 판정 | 하네스에 1초씩 앞으로 가는 가짜 시계를 넣어 실제 실행 간격을 흉내 냄 |
| 목표 달성률이 90.9% (12개월 내내 "미달") | 목표 생산량 계산에 주말 감산·가동률을 반영하지 않음 | 목표 계수를 0.93 → 0.86 으로 조정해 달성률이 95% 언저리에서 오르내리도록 |

## 4. ②에서 실제 구글 환경이 가르쳐 준 것 → 이 프로젝트의 설계 조건

로컬 하네스로는 잡히지 않고 **실제 Apps Script 에 올린 뒤** 나타났던 오류들입니다. ③은 이것을 처음부터 조건으로 넣었고, 하네스가 같은 상황을 재현합니다.

| ②에서 난 오류 | 원인 | ③의 설계 |
|---|---|---|
| `ReferenceError: SH is not defined` | 최상위 배열이 다른 파일의 상수를 **로드 시점에** 참조. Apps Script 는 파일 실행 순서를 보장하지 않음 | 탭정의·설정기본값·라인정의를 **함수**로. 하네스는 `SH` 를 정의하는 `Code.js` 를 **마지막**에 로드 |
| `Service Spreadsheets timed out` 로 설치 중단 | 수식 1만 개 쓰기·행 삭제 직후 구글이 잠깐 응답 못 함(일시적) | 무거운 호출을 `_재시도()`(1.5초·3초, 최대 3회)로. 회귀 테스트: 1회 실패는 통과, 3회 실패는 오류 그대로 |
| `You can't create a filter in a sheet that already has a filter` | 재실행 때 `createFilter` 가 거부됨 | 기존 필터 `remove()` 후 재생성. 하네스 스텁이 같은 거부를 재현 |
| `Converting ... is not supported` (xlsx) | `getAs` 변환이 계정에 따라 막힘 | `_내보내기()` 3단계: getAs → 다운로드 URL(+OAuth 토큰) → 구글시트 사본 보존. 어느 경로를 썼는지 로그 |
| 내보낸 대장이 죽음 (`requireValueInRange`) | 데이터 검증 범위 참조는 **같은 스프레드시트** 안에서만 | 드롭다운은 전부 `requireValueInList`(값 목록). 하네스 스텁은 범위 참조를 거부 |
| 설치가 수 분씩 걸림 | 수식 반복문 안에서 행마다 설정 탭을 다시 읽음(수만 번 API 왕복) | 설정·생산일보·라인·목표를 한 실행 안에서 한 번만 읽는 캐시, 쓰면 무효화 |
| 검증이 `21부` 로 셈 | 발행이력에 빈 줄·중복 줄이 섞임 | `정리_측정로그중복()` 을 `설치_전체` 가 자동 호출, `설치_확인` 이 검사. 회귀 테스트: 빈 2·중복 1 주입 → 정리 |
| `Cannot read properties of undefined` | 내부 함수를 편집기에서 인수 없이 실행 | `_` 함수 8개가 "메뉴 [대시보드] → … 으로 실행하세요" 로 안내. 회귀 테스트로 전부 확인 |
| 6분 제한 | 무료 계정 1회 실행 제한 | 샘플 데이터는 2,000행씩 나눠 쓰고 진행 위치를 저장 → 재실행 시 `[이어서]`. 회귀 테스트: 중단 → 이어쓰기 → 5,475행 |
| (새로 대비) 차트가 재실행마다 쌓임 | `insertChart` 는 기존 차트를 지우지 않음 | `_차트전부삭제()` 후 재생성. 회귀 테스트: 재설치·갱신 후에도 6개 |
| (새로 대비) 조건부 서식이 조용히 무시됨 | 다른 시트 참조 | 같은 시트의 기준값만 참조. 하네스 스텁이 다른 시트 참조를 거부 |

> 교훈 두 가지. ① **실제 환경에서 난 오류는 하네스 스텁으로 바꿔 둔다** — 그러면 다음 프로젝트에서는 올리기 전에 잡힌다. ② 실패를 `try/catch` 로 삼키지 않는다. 건너뛰면 `[건너뜀]` 로, 재시도하면 `[재시도]` 로, 대체 경로면 `[대체]` 로 로그에 남긴다.

## 5. 실제 구글 환경에서 확인해야 하는 것 (하네스가 못 보는 것)

- 대시보드 카드·차트의 **실제 배치**(차트 크기 560×340, 2열 × 3행)와 콤보 차트(파레토)의 두 번째 축 표시
- ~~리포트 PDF 의 1페이지 맞춤~~ → 실제로 2장으로 갈라져서 고쳤습니다(아래 6절)
- `설정`·`목표`·`집계` 의 월 값이 텍스트로 유지되는지 → `설치_확인` 항목 7·8
- 실제 소요 시간: `설치_샘플데이터` 는 수식 16,425개 + 차트 6개라 1~3분 예상
- 이 항목들을 실행한 뒤 화면을 저장해 README 에 "실제 화면" 절로 추가할 예정입니다.

## 6. ③을 실제로 돌려 보고 고친 것 (2026-09-25)

하네스가 초록이어도 **화면은 따로 봐야 한다**는 것을 보여 주는 사례입니다.

| 증상 | 원인 | 수정 |
|---|---|---|
| 리포트 PDF 가 2장으로 갈라지고, `5. 조치 제안` **제목만 앞장 끝에** 남고 내용이 다음 장으로 밀림 | 행 높이를 기본값(21px)으로 두어 45행이 A4 한 장(약 978px)을 넘겼다. 내보내기 옵션도 가로 맞춤(`fitw`)만 걸려 있었다 | ① 행 높이를 조였다 — 표·본문 17px, 종합 코멘트 60px, 조치 제안 30px, 서명란 32px → 총 847px. ② 종합 코멘트와 조치 제안을 다른 스타일로 분리(한 줄짜리 조치 제안에 64px를 주던 것을 30px로). ③ 내보내기 URL 에 **세로 맞춤(`fith=true`)** 과 여백 0.4인치를 추가(가로 맞춤만으로는 세로가 넘쳤다). ④ 실행 로그에 `예상 높이 약 847px / A4 세로 1장 978px` 를 남기고, 하네스가 **모든 행에 높이가 지정됐는지 + 총 높이 < 978px** 를 단언하도록 회귀 테스트 추가 |

> 교훈: 표·차트·PDF 처럼 **모양이 결과물인 기능**은 로그가 정상이어도 사용자가 화면을 봐야 끝난다. 그래서 고칠 때 "다시는 안 갈라지게" 하는 숫자(총 높이)를 로그와 테스트로 남겼다.

## 7. 이 프로젝트에서 증명하는 것

- 같은 도구 함수·같은 문서 구조로 **세 프로젝트를 한 계열**로 만드는 일관성
- 앞선 프로젝트의 **실제 오류를 설계 조건과 회귀 테스트로 승격**시키는 습관
- 시트 수식(SUMIFS)과 스크립트를 역할에 따라 나누고, 둘의 **정의를 같게** 맞추는 감각
- 무료 계정의 6분 제한·일시적 오류·엑셀 호환을 전제로 한 설계(분할·이어쓰기·재시도·값 굳히기)
- 데이터에서 **사람이 읽을 문장**(종합 코멘트·조치 제안)까지 자동으로 뽑아내는 것

## 8. 남은 개선 아이디어

- 생산일보 입력을 구글 폼/설비 로그 CSV 에서 자동으로 받아 `대시보드갱신` 트리거와 연결
- 라인별 월별 히트맵(월 × 라인 불량률) 탭 추가 — 급증을 표에서도 한눈에
- 리포트 PDF 를 슬라이드(구글 프레젠테이션) 1장으로도 내보내기
- 수만 행 규모라면 생산일보 수식 3열을 값으로 굳히고 갱신 때만 다시 계산
